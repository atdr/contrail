# contrail v0.1.0 build plan

Date: 2026-08-14

## Context

A working single-file prototype (`prototype/sync.py`, ~435 lines) already pulls flights from a
TripIt iCal feed, prices them with Google's Travel Impact Model API, and maintains a CSV with a
cumulative CO2e total. Its parsing regexes, exact-then-typical emissions fallback, and CSV
sort/recompute logic have been validated against a real TripIt feed and are correct.

What's missing is everything around that logic: a package structure, plugin seams for future
importers/emissions providers/storage backends, and a two-repo production setup that keeps
open-source code and personal flight data strictly separate.

The outcome is three GitHub repos under `atdr`:

- **`atdr/contrail`** (public) — the installable package. All logic, no secrets, no personal data.
- **`atdr/contrail-gh`** (public) — a GitHub *template* repo. A workflow, a header-only CSV, and
  setup docs. Users create their own **private** repo from it and add their own secrets.
- **`atdr/my-contrail`** (**private**) — your personal production instance, created *from* the
  template, holding your real flight history and your GitHub Actions secrets. This is both the
  thing you actually run and the end-to-end proof that the template works.

None of the three exist yet. `/Users/andreas/dev/contrail` is empty and not a git repo. `gh` is
authed as `atdr`.

**This is a port, not a reimplementation.** The prototype's logic moves into
`src/contrail/...` largely unchanged and picks up one deliberate schema change (§3.5 of the
briefing).

## Part 1 — `atdr/contrail` (the package)

### 1.1 Scaffolding

- [ ] `git init` in `~/dev/contrail`, branch `main`
- [ ] `pyproject.toml` — hatchling backend, static `version = "0.1.0"` (release-please rewrites
      it; no dynamic/VCS versioning), `requires-python = ">=3.10"` (the briefing's `str | None`
      annotations need it), deps `requests>=2.31` + `icalendar>=5.0`, extras
      `yaml = ["pyyaml>=6"]` and `dev = ["pytest>=8", "ruff>=0.6"]`, script entry
      `contrail = "contrail.cli:main"`, plus a `[tool.ruff]` section
- [ ] `src/contrail/__init__.py` — `__version__` read via `importlib.metadata.version("contrail")`
      so there is exactly one source of truth and release-please only ever edits `pyproject.toml`
- [ ] `LICENSE` (MIT, 2026 Andreas Richardson), `.gitattributes` (`* text=auto`)
- [ ] `.gitignore` — **must** cover `config.json`, `config.yaml`, `flight_emissions.csv`,
      `.env*`, `venv/`, `__pycache__/`, `*.egg-info`. This repo is public and its documented
      default behaviour is to write `./flight_emissions.csv` in the cwd, so an un-ignored CSV is
      a real leak path.

### 1.2 `src/contrail/models.py`

Dataclasses as §3.2: `FlightRecord`, `UnparsedEvent`, `EmissionsResult`. Add one shared
`key` property returning `f"{source}:{source_id}"` — the namespaced dedup key used by the
importers, the emissions provider's result dict, and the CSV.

**One additive change to `UnparsedEvent`:** a `partial: dict = field(default_factory=dict)`
field. The prototype (`sync.py:396-413`) keeps whatever it *did* extract on an unparsed row,
blanking only the fields that failed; the briefing's three-field model structurally can't. That
loss matters most for `flight_date`: `recompute_cumulative` (`sync.py:308-312`) falls back to
`datetime.min` for an unparseable date, so date-less rows sink to the top of the CSV permanently
and sit outside the chronological cumulative sequence — whereas a preserved date sorts into
place, so filling emissions in by hand later just works. Partial airports are also enough to
price via `computeTypicalFlightEmissions`, which only takes a market.

The Protocol is unchanged and `partial` defaults empty, so future importers can ignore it
entirely. Relatedly, `tripit_ical` populates `raw_text` with SUMMARY + DESCRIPTION + LOCATION,
not SUMMARY alone — the prototype's `raw_summary` omitted the very fields a parse failure most
often hides in, making the "check `raw_summary` and fill it in manually" workflow unreliable.

`EmissionsResult` holds **grams** (ints, as TIM returns them). The grams→kg conversion lives in
storage only, so the API layer stays a faithful mirror of the upstream response.

### 1.3 `src/contrail/importers/`

- `base.py` — `Importer` Protocol: `id: str`, `fetch(config: dict) -> Iterable[FlightRecord | UnparsedEvent]`
- `tripit_ical.py` — direct port of the prototype's `AIRPORT_CODE_RE`, `FROM_TO_RE`,
  `CODE_PAIR_RE`, `FLIGHT_NO_RE`, `_extract_from_blob`, `extract_flight_fields`,
  `is_flight_event`, `parse_flights_from_ical` (`prototype/sync.py:110-218`). Copy the regexes
  character for character. Emits `FlightRecord` when all of carrier/number/origin/destination/date
  resolve, `UnparsedEvent` (with whatever resolved in `partial`) otherwise. `source_id` is the
  iCal UID; `cabin_class` stays `None` (TripIt's feed doesn't carry it).
- `__init__.py` — `IMPORTERS: dict[str, type[Importer]]` registry plus `get_importer(name)` that
  raises with the list of valid names. Adding an importer later = one file + one registry line.

**Addition beyond the briefing:** `fetch` accepts a local filesystem path or `file://` URL as
well as `http(s)://`. This is what lets CI run `contrail sync --dry-run` against the `.ics`
fixture with no mocking and no network (§6 requires that check).

### 1.4 `src/contrail/emissions/`

- `base.py` — `EmissionsProvider` Protocol: `compute(flights) -> dict[str, EmissionsResult]`,
  keyed by dedup key
- `tim.py` — `TIMEmissionsProvider(api_key)`, porting `compute_exact_emissions` and
  `compute_typical_emissions` (`prototype/sync.py:229-284`) unchanged in substance: batch of 200,
  market-deduped typical fallback, `modelVersion` recorded only on `exact` rows. Only the dict
  keys change (uid → `source:source_id`) and results become `EmissionsResult` instead of tuples.

Hybrid flow stays exactly as the prototype: batch `computeFlightEmissions` first; anything coming
back empty (i.e. already departed — a property of Google's API, not a bug) goes into a batched
`computeTypicalFlightEmissions` call.

### 1.5 `src/contrail/storage/`

- `base.py` — `Storage` Protocol: `load() -> list[dict]`, `save(rows) -> None`
- `__init__.py` — shared `recompute_cumulative(rows)` free function (ported from
  `prototype/sync.py:306-324`), living outside the protocol so any future backend inherits the
  same sort/recompute invariant. The CLI calls it before `storage.save()`.
- `local_csv.py` — `LocalCSVStorage(path)` with the §3.5 schema:

  `sync_timestamp, source, source_id, flight_date, carrier_code, flight_number, origin,
  destination, cabin_class_known, emissions_source, model_version, emissions_kg_first,
  emissions_kg_business, emissions_kg_premium_economy, emissions_kg_economy,
  emissions_kg_actual, cumulative_kg_actual, raw_summary`

  `emissions_kg_actual` = `emissions_kg_{cabin_class_known}` when the source knew the cabin, else
  `emissions_kg_economy`. `cumulative_kg_actual` is the running total of that column sorted by
  `flight_date` — the headline number, replacing the prototype's `cumulative_kg_economy`.

**Addition beyond the briefing:** `load()` detects a legacy prototype header (`tripit_uid` /
`cumulative_kg_economy`) and migrates in memory on read — `tripit_uid` → `source_id` with
`source = "tripit_ical"`, `emissions_kg_actual` ← `emissions_kg_economy`, cumulative recomputed.
Without this, pointing v0.1.0 at an existing prototype CSV re-imports every flight and burns API
calls. Cheap to add, worth flagging as a scope addition.

### 1.6 `src/contrail/config.py` and `cli.py`

Resolution order, highest first: CLI flags → env vars → `config.json`/`config.yaml` in cwd →
built-in defaults. Env vars are primary because that's what every deployment target injects.

Config shape:

```json
{
  "csv_path": "flight_emissions.csv",
  "sources": [
    { "type": "tripit_ical", "url": "https://www.tripit.com/feed/ical/private/.../tripit.ics" }
  ],
  "emissions": { "provider": "tim", "api_key": "..." }
}
```

- `sources` is a list from day one; the CLI loops over every entry in a single `sync`.
- With no config file, `TRIPIT_ICAL_URL` synthesizes a single implicit `tripit_ical` source, so
  the env-var-only path stays a one-liner. `TIM_API_KEY` and `CSV_PATH` override their file
  counterparts.
- YAML support via a lazy `import yaml`; if `config.yaml` exists but PyYAML isn't installed, fail
  with "install `contrail[yaml]`" rather than a traceback. Keeps runtime deps at two.
- No `--csv-path`/`CSV_PATH` → `./flight_emissions.csv` in the cwd. Per §3.6 this unconfigured
  path must always work out of the box.

CLI (argparse):

```
contrail sync [--config PATH] [--csv-path PATH] [--dry-run]
contrail sources
```

`sync` flow: load config → `storage.load()` → build `{source}:{source_id}` key set → for each
configured source, `fetch()` and drop anything already keyed (also dedup within the run) →
`--dry-run` prints what would be written and stops here → else `provider.compute()` → build rows
→ `recompute_cumulative` → `storage.save()` → print the prototype's summary lines (rows added,
kg added, new cumulative total, unparsed count).

**Addition beyond the briefing:** `--dry-run` does not require `TIM_API_KEY`, since it never
calls the emissions API. This is what makes the CI fixture check runnable without a secret.

`sources` lists registry entries and marks which are configured.

### 1.7 Tests (`tests/`)

pytest, `unittest.mock.patch` for HTTP (no `responses` dep). **No test makes a real network
call** — §6 is non-negotiable.

- `fixtures/sample_feed.ics` — fully synthetic (fake carriers/routes, never the real itinerary):
  a `[Flight]`-tagged event parseable from SUMMARY alone, one parseable only from
  DESCRIPTION+LOCATION, one flight-tagged but unparseable, a train and a hotel event that must
  **not** be detected, and both date-only and datetime `DTSTART` forms.
- `test_tripit_ical_importer.py` — detection incl. correct exclusions, SUMMARY-first precedence,
  DESCRIPTION/LOCATION fallback, `UnparsedEvent` emission *with* its `partial` fields populated,
  date handling.
- `test_tim_emissions.py` — mocked `requests.post`: exact-only path; empty result triggers typical
  fallback; two flights on one route produce one market in the fallback body; >200 flights batch.
- `test_local_csv_storage.py` — round trip; cumulative recompute after inserting a row out of date
  order; `emissions_kg_actual` picks the cabin column when known; legacy-header migration; an
  unparsed row with a `partial` date sorts chronologically rather than to the top.
- `test_config.py` — flag > env > file > default; env-only synthesizes a `tripit_ical` source.

### 1.8 CI (`.github/workflows/ci.yml`)

Push + PR. Two jobs:

- **lint** — `ruff check` and `ruff format --check` on a single Python version.
- **test** — matrix Python 3.10–3.13: `pip install -e ".[dev]"`, `pytest`, then
  `contrail sync --dry-run --csv-path /tmp/out.csv` with `TRIPIT_ICAL_URL` pointed at
  `tests/fixtures/sample_feed.ics`. Per §6 this runs on `contrail`, not `contrail-gh`, so a
  broken parser is caught before anyone's pinned production instance picks it up.

### 1.9 Release + dependency automation

- [ ] `.github/workflows/release-please.yml` — `googleapis/release-please-action@v4` on push to
      `main`, `release-type: python`, permissions `contents: write` + `pull-requests: write`. It
      maintains a rolling release PR, and on merge bumps `pyproject.toml`, writes `CHANGELOG.md`,
      tags, and cuts the GitHub release. `CHANGELOG.md` is therefore generated, never hand-edited.
- [ ] `release-please-config.json` + `.release-please-manifest.json` seeded to `{".": "0.1.0"}`,
      so the first automated release after the manual v0.1.0 tag is 0.1.1 / 0.2.0 rather than
      restarting at 1.0.0 (release-please's default first release).
- [ ] `.github/dependabot.yml` — `pip` and `github-actions` ecosystems, weekly, with
      `commit-message: {prefix: "chore", include: "scope"}` so its PRs are themselves conventional
      commits (`chore(deps): ...`) and don't break release-please's parsing.
- [ ] `.github/workflows/pr-title.yml` — `amannn/action-semantic-pull-request` validating PR
      titles. Squash-merge titles become the commit subjects release-please reads, so an
      unvalidated title silently drops a change from the changelog.
- [ ] `.pre-commit-config.yaml` — ruff lint + format, trailing whitespace, EOF fixer. Optional to
      install locally; CI is the real gate.
- [ ] All commits conventional (`feat:`, `fix:`, `chore:`, `docs:`, `test:`), atomic, under 72
      chars, per the scaffold → models → importers → … sequence in Part 3.

Known gotcha to document, not fight: PRs opened by the default `GITHUB_TOKEN` (release-please's
included) do not trigger other workflows, so the release PR itself won't show a CI run. The
commits it releases were already tested on `main`.

Branch protection on `main` is deliberately **not** enabled — release-please works fine either
way, and for a single-maintainer repo required-PR flow mostly gets in the way. Easy to add later
if that changes.

      via the Actions tab's **Run workflow** button. Per your answer, this first run is the

      departed. That's the API's behaviour, not a defect — from here on, the daily 15:37 UTC run
      catches upcoming flights while they can still get an `exact` number.
- [ ] Review the resulting commit: row count plausible, `cumulative_kg_actual` sane, any

## Flags

- **Python 3.7 is the default `python3` here.** Everything above uses `/usr/local/bin/python3.12`.
- Four deliberate additions beyond the briefing, each called out in place: `UnparsedEvent.partial`
  + richer `raw_text` (preserves prototype behaviour the briefing's model would drop), local-path
  fetch (needed for the CI check §6 mandates), `--dry-run` not requiring a TIM key (same reason),
  and legacy-CSV migration on read. That last one now has no immediate user — you're starting
  `my-contrail` empty — but it stays, since it's cheap, tested, and the failure it prevents
  (silently re-importing and re-pricing an entire history) is expensive.
- **I never touch your secrets.** You set `TRIPIT_ICAL_URL` and `TIM_API_KEY` on `my-contrail`
  yourself (Part 4). If you'd rather I ran the live local sync in step 1 of Verification, that
  requires exporting them into a shell I can see — your call, and skipping it costs nothing since
  Part 4 covers the same ground.
- The briefing's §3.5 CSV schema is treated as fixed. Since `contrail-gh` ships a header-only CSV
  and derived repos accumulate real data against it, any later column change is a breaking change
  for every existing instance — so it's worth a last look now rather than at v0.2.0.
